This is the work I do at my SCADA engineering internship at PT PGAS
Telekomunikasi Nusantara. Monitoring OT equipment is not hard because the
protocols are exotic; it's hard because every PLC, HMI, network device and
gas process instrument gets configured by hand, one at a time, and nobody can
tell you afterwards what is actually being watched.

## One file is the truth

The whole system is driven by a single YAML catalog covering four OT/ICS asset
classes. A Python engine reads it and provisions Zabbix through the API:
hosts, templates, items, triggers. Change the catalog, re-run, and the server
matches it.

```yaml
# one entry in the asset catalog — everything downstream is generated
- class: plc
  host: plc-metering-01
  templates: [tpl.plc.health, tpl.modbus.core]
  triggers:
    - key: cpu.load
      warn: "> 70"
      fail: "> 90"
```

## You can't rehearse on a live pipeline

The obvious problem with alerting logic for gas transmission is that there is
no safe way to test it. You cannot make a real compressor misbehave to find
out whether your trigger fires.

So the lab includes a telemetry simulator that generates synthetic SCADA
sensor data, which means dashboards and alert rules get validated against
failure conditions long before anything is pointed at production. On top of
that sits a three-tier health model — good, underperforming, failed — with
correlation-based failure-chain detection across the SNMP-monitored
parameters, so a cascade reads as one event rather than forty alarms.
